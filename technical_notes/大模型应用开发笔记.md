# 大模型 RAG 系统搭建实践笔记

> 项目：内部知识库问答系统（基于企业内部 Wiki）
> 作者：AI 平台团队 / 张同学
> 最后更新：2026-04-02

## 背景与目标

公司内部 Wiki 累积 3 万+ 文档，员工搜索体验差（关键词精确匹配，容错能力弱）。
目标：基于 LLM + 向量检索搭建自然语言问答系统，召回率 > 85%，答案准确率 > 75%。

## 架构设计

### 总体链路

用户提问 → 意图识别 → 语义检索（向量库）→ BM25 混合召回 → 重排 → LLM 回答 + 引用溯源

架构示意见 `assets/rag架构图.png`。

### 关键组件选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 向量库 | Milvus 2.4 | 自建，数据安全可控 |
| Embedding 模型 | bge-large-zh-v1.5 | 中文场景性价比最高 |
| 重排模型 | bge-reranker-base | 在公司数据上 NDCG@10 提升 12% |
| LLM | Claude Sonnet 4.5（主）+ 内部小模型（兜底） | Claude 支持长上下文，引用溯源准 |

## 实施过程中踩的坑

### 坑 1：chunking 策略影响巨大

- 最初用固定 512 token 切块，检索效果很差
- 改为"语义边界 + 滑窗"后 recall@10 从 62% 提升到 81%
- 经验：chunking 绝对不能套默认参数，要针对文档结构调整

### 坑 2：向量检索 + 关键词检索必须混合

- 纯向量召回对专有名词（内部系统名、缩写）效果差
- 加上 BM25 后专有名词查询 recall 提升 20+ 百分点
- 最终采用 RRF（Reciprocal Rank Fusion）融合两路召回

### 坑 3：引用溯源是用户信任的关键

初版系统答案准确率尚可，但用户不信任，因为不知道答案从哪来。
加入"引用块高亮 + 原文跳转"后，系统使用率从 38% 涨到 72%。

这启发我们：**可解释性 > 准确率本身**。

## 评估方法

### 离线评估

- 构建 500 条标注数据集（由 PM 抽样 + 人工标答）
- 召回率（recall@10）、答案准确率（人工评估）、引用准确率（自动计算）

### 在线评估

- A/B 实验：50% 流量新系统，50% 老搜索
- 指标：首次点击率（CTR）、会话时长、"没找到答案"按钮点击率
- 结果：CTR +18%，"没找到"按钮 -35%

## 后续优化方向

1. **Query 改写**：把口语化的问题转成更精确的检索式
2. **Multi-hop**：支持跨文档推理（当前只做单跳）
3. **引用质量提升**：同样的答案，优先引用权威来源而非 UGC 文档
